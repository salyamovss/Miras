# Backend foundation

## Application shape

Miras is a Java modular monolith: one Spring Boot application and one PostgreSQL
database, divided into modules with explicit responsibilities. The public site
and the separately addressed admin interface will be frontend clients of the
same backend API.

Initial modules:

- **catalog** owns material records, localized metadata, and author attribution.
- **identity** owns administrator accounts and roles. Public visitors do not
  have accounts. Super Admin provisions staff accounts; password reset is out
  of the initial scope.
- **publication** owns submission/review decisions. Admin submits material;
  Super Admin approves or rejects it. Approval makes it eligible for the public
  catalog.
- **media** owns metadata for source files. The original files will later live
  in S3; S3 and Elasticsearch are deliberately not configured in this stage.

Modules are package boundaries inside the same app. A module may use another
module through its published application interface; modules should not reach
into another module's persistence implementation.

### Java package convention

Each module keeps persistence, transport, and use-case code separate:

```text
<module>/
  dal/entity/       JPA mapping only; Lombok generates accessors
  dal/repository/   Spring Data repository interfaces
  dal/enums/        persisted enum codes, separate from entities
  mapper/           MapStruct mapping interfaces; implementations are generated
  dto/request/      incoming API/service data contracts
  dto/response/     outgoing API/service data contracts
  service/          public use-case interface
  service/impl/     use-case implementation and orchestration
```

Entities contain persistence fields and mapping annotations only. Business
transitions and use cases belong to service implementations. DTOs are separate
from JPA entities so API shape can evolve without exposing database mappings.
The current catalog draft-saving and publication-decision use cases follow this
convention. MapStruct interfaces live in `mapper/`; Maven generates their
implementations at compile time. Hand-written loops for copying DTO fields are
avoided. A linear loop generated by MapStruct is expected for collections; its
cost is proportional to the number of input rows, while database round trips are
managed separately with bulk repository operations such as `saveAll`.

Shared API errors are returned by one `@RestControllerAdvice`: malformed input
(400), missing resources (404), conflicting state (409), unauthenticated access
(401), and forbidden operations (403). Unexpected errors return a generic 500
response without exposing internal exception details. Domain checks remain in
service implementations; the exception handler only converts errors to HTTP
responses.

UUID primary keys are generated by JPA/Hibernate (`GenerationType.UUID`), not
inside entity constructors. Translation and material-author join rows use
composite keys: their IDs are a material UUID plus a locale or author UUID.

## First domain model

```text
AdminUser 1 ── * Material (createdById)
Material 1 ── * MaterialTranslation (one per ky / ru / en)
Material * ── * Author (through MaterialAuthor, with display order)
Material 1 ── * MaterialFile (each file has its own language)
AdminUser 1 ── * MaterialFile (uploadedById)
Material 1 ── * PublicationRequest (one record per submission/review attempt)
AdminUser 1 ── * PublicationRequest (submittedById / reviewedById)
```

The cross-module references are stored as UUIDs. PostgreSQL foreign keys protect
referential integrity; application services will call the owning module's
published interface instead of importing another module's persistence classes.

### Material metadata

The material has one translation row for each supported interface language:
Kyrgyz (`ky`), Russian (`ru`), and English (`en`). The first changeset stores a
title and short description per language. Those values may be incomplete while
the material is a draft; submission validation belongs in the application
workflow. Super Admin can complete or correct a translation during review. The
actual book/video/image file is not translated automatically; each uploaded
file records its real language.

The material also stores its type, primary language, country, year/period,
categories/keywords, creation/recording place, and access-condition code. The
initial type codes are `BOOK_RESEARCH`, `AUDIO`, `VIDEO`, and `PHOTOGRAPHY`; the
final option list and localization labels should still be checked against the
complete form/TZ.

Authors are separate from the administrator who creates/submits the record.
A material can have multiple authors, kept in the order entered by staff.

### Review requests

The material remains in the catalog module. Each submit action creates a
`PublicationRequest` in the publication module with status `PENDING_REVIEW`; the
super admin changes it to `APPROVED` or `REJECTED`. A resubmission creates a new
request record, preserving prior decisions and timestamps. Public visibility is
determined by an approved request, not a status field on the material.

### File records

The first schema stores file metadata and a storage key, not file bytes. The key
will later identify an S3 object. Each file has a language, original filename,
media type, size, uploader, and source/rights-holder value. The form currently
shows PDF, MP3, MP4, JPG, and TIFF with a 2 GB upload limit. OCR, PDF text
extraction, video transcription, and Elasticsearch indexing are future
processing stages; they do not change the catalog's source records.

## Deliberately unresolved

- Final material-type options and labels.
- Exact meaning of “read-only” versus open access, and whether it controls online
  reading, downloading, or both. The researcher-request option is excluded from
  the initial model because the public site has no account or request workflow.
- OCR and video transcription requirements.

These choices should be resolved before adding corresponding fields or external
integrations, rather than guessed in the initial schema.
